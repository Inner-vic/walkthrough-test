# 走查原生日志的来源身份与执行边界

本协议解决跨来源同名日志在原生收集和主题提取时被平铺、覆盖或拒绝的问题。原始文件名继续用于显示、前缀匹配及部署原生时间谓词；文件名本身不再承担对象身份。协议不删除冲突来源、不猜测归属、不进行全局日志行去重，也不分别计算来源百分位后再合并。

## 身份：下载对象、归档成员、逻辑成员

一个输入制品由可信的外层来源目录、输入根目录内的相对路径、完整文件 SHA-256 和字节数绑定。来源只取外层的 `log_fsdA`、`log_fsdB`、`log_xcu_mcu` 或 `log_bzcu_eth`，不从 ZIP/TAR 内路径、日志内容或文件名前缀推断；显式旧格式输入只能标记为 `legacy`。外层路径出现多个来源类别时停止。

`source-catalog-v1` 保留每个制品及每个完整成员路径。`origins` 的 `member_path` 是经过安全路径检查的完整内层路径，`archive_member_name` 保留归档声明的原始拼写。ZIP 使用未被平台文件名规范化覆盖的 `orig_filename`；普通 `.log` 文件的两者固定为原始 basename。制品摘要继续绑定完整原始归档。

逻辑成员按 `(source, original basename, content SHA-256, bytes)` 标识，ID 为这组字段规范 JSON 的完整 SHA-256。同来源、同名、同内容的重复归档合并为一个逻辑成员，但所有制品和完整成员路径仍保留在有序 `origins` 中。这样保留既有同来源重复归档只消费一次的口径。跨来源即使同名、同内容，也分别保留并参与该来源的选择；真实不同来源的不同内容不得因为文件同名而丢失。

同一来源、同名而内容不同的多个逻辑成员，如果任何一个进入精确原生选集，立即停止，避免任意覆盖或重复计数。均在原生选集之外的冲突仍完整保留，不阻塞本窗统计。Windows 大小写别名按同样保守规则处理。

## Catalog：只读验证与复制前后绑定

`source_catalog.build_catalog()` 只读扫描输入，计算完整制品摘要和成员内容摘要，保留稳定的制品及逻辑成员 `ordinal`。输入遍历按相对路径排序，归档内按验证后的原始成员顺序；重复逻辑成员沿用首次验证时的顺序，后续来源追加到 `origins`。

扫描继续执行原有归档路径、链接、特殊文件、加密 ZIP、重复路径、Windows 非法名和别名检查。嵌套归档、未支持的压缩文本、隐式 `message` 配对、未解码二进制及大写 `.LOG` 不会被当作完整文本日志。输入总字节、全部展开成员数量和展开字节有明确上限；非 `.log` 的普通成员也计入展开预算。读取 ZIP 日志时由完整流读取校验 CRC，所有日志核对声明大小与实际长度。

每个制品在扫描前后重新计算摘要，私有输入复制后再次建立 catalog，要求复制前后的完整 catalog 相等。顶层 `catalog_sha256` 绑定其余全部字段；`validate_catalog()` 严格检查类型、身份摘要、路径、引用、顺序、准入关系和预算，不会把任意 JSON 标签当作真实消费证明。实际执行另有独立原谓词重放。

## Stage：保留全部归档准入日志

`materialize_catalog()` 将全部 `eligible=True` 的逻辑成员写入：

```text
input/perf/members/<member_id>/<original_basename>
```

`eligible` 仅表示原生外层归档时间谓词准入，普通 `.log` 直接准入；它不等于规则前缀或日志时间选中。所有归档准入日志均暂存，包括不匹配规则前缀、早于统计窗或晚于第一条边界日志的成员，以保持原生递归 VIN/版本识别的输入范围。原生外层时间谓词不准入的归档仍接受安全验证并保留证明，但不进入 VIN/版本扫描。

暂存不使用 `extractall`，不创建来源文件的符号链接。目标须为空目录，所有路径受控，逐个成员验证原始归档成员拼写、大小、内容摘要及实际写入摘要；所有输入制品在暂存前后再次核验。只有完整成功后才返回 `source-materialization-v1` 回执。失败产生的目录不能作为成功输入或下次自动可复用缓存。

## Selection：原始文件名、原始谓词、来源独立状态

策略为 `source-namespace-v3`。完整 201 项规则快照、部署 `CONFIG_PATH`、原始请求时间窗及原始时间解析/选择函数共同决定选集。`selected_member_ids` 是完整规则的精确成员并集，不是全部准入成员，也不是包含所有同秒边界候选的保守包络。

显式 `RecordPerformance.extract_logs` 适配器安装前必须验证原始完整方法 AST 与已批准版本相同。适配器以原始 basename 匹配原始前缀、调用原始 `_parse_cn_dt_from_log_path` 和 `should_keep_log`；Windows 匹配保持原生大小写行为。按原时间解析结果排序，同秒按稳定 `ordinal` 排序，每个 `(source, prefix)` 独立维护 `kept_first_after_end`。因此每个来源各自保留原生定义的第一条窗后日志，同秒只保留精确顺序中的第一条。

每个主题的原生输入位于：

```text
input/perf/log/<native_scope>/<member_id>/<original_basename>
```

同一主题一次返回全部入选来源的文件列表，按原始 basename 与稳定顺序排列。其后的原生 tag 预筛选、grep/AWK、CSV 处理、计数、去重、差分、均值及百分位算法继续使用部署代码；不按来源分别运行统计后拼合结果。

## Actual consumption：独立证据与失败闭锁

`source_runtime_audit` 独立解析文件名时间、重放前缀及来源边界策略。它核对真实 collector 全集、暂存回执、INI 时间/目录、`RecordPerformance` 构造器参数、完整规则主题覆盖、实际谓词调用及每次提取返回的有序 ID、路径、字节数和摘要。实际返回路径中的 basename 必须仍是 catalog 的原始 basename；同名成员以 ID 区分。

每主题精确选集、真实消费并集和 catalog 的完整规则选集必须一致。原生代码即使捕获了适配器或审计异常，错误仍被锁存，最终不得导出成功统计。指标输入诊断沿用原生返回的实际成员路径与内容摘要，不自行按 basename 重关联。该证据证明原生消费入口与字节，不凭空证明日志体持续覆盖或车辆全部链路都已上报。

## 环境、缓存与交付

Base 与 PCM 更新两窗独立按 Prod→Test 查询，允许两窗分别选择不同环境；同一窗的五类查询固定绑定同一个候选环境。只有明确成功且为空的查询才进入下一环境；网络、鉴权、格式或分页异常必须停止，不视为空。已验证的 Prod 首屏成功 `data:null` 仅按既有明确成功信封的窄兼容契约处理，并保留有限兼容证据，不能接受缺失 data、未知成功状态或任意内部 marker。

Windows 新分析 profile 为 `m100-full-native-audited-v11-windows-native`，与来源 catalog、命名空间策略、当前解释器/工具绑定及执行 release 一起校验。旧 v10 的原生结果、输入计划或 Windows 执行绑定不得通过修改标签混入 v11。旧 final 保持原 release 的冻结交付语义，不迁移或重算；需要原始数据重放时使用独立工作目录，保留精确旧 record、输入和规则的来源摘要。

错误通过有限阶段和原因表达：本地预检、身份/授权、环境查询、下载、原生输入校验、原生执行和交付各自保留原有失败闭锁。新增原生失败协议区分 `input_validation` 和 `native_execution`，对外只提供固定消息；原始异常、路径、URL、令牌、任意服务端文本留在受控内部诊断中，不进入普通用户回复。缺少任何来源、字节或消费证明时，不能把未完成分析描述为完成报告。
